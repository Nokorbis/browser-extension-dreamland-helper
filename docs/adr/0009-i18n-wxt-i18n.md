# 0009. Localize UI text with @wxt-dev/i18n

Status: Accepted

Date: 2026-07-23

## Context

Dreamland Reborn QoL targets **dreamland-reborn.net**, a forum whose roleplay is written in
French, so its audience is effectively French-only. Until now every user-facing string — the
four feature `name`/`description` pairs, the popup `soon` badge, and the (absent) store
description — was a hardcoded English literal scattered across feature files and the popup.

The strings needed to be French. Two options were on the table:

1. **Translate the literals in place** — replace each English string with French. Zero new
   dependencies, no new pattern, but UI text stays scattered and adding a second language
   later means re-doing the work.
2. **Adopt an i18n layer** — move all UI text into a catalog referenced by key. The forum is
   French-only today, so this is not strictly required, but it centralizes UI text (matching
   how `[[0005-centralize-phpbb-dom]]` centralizes DOM knowledge and how the typed settings
   layer `[[0006-typed-settings-storage]]` centralizes persistence) and makes a future
   language a one-file addition.

Within option 2, the native `browser.i18n` / `_locales` mechanism works but is verbose and
untyped. `@wxt-dev/i18n` sits on top of it: it compiles a per-language catalog
(`src/locales/<lang>.yml`) into `_locales/<lang>/messages.json`, generates TypeScript types so
`i18n.t('...')` keys are checked by `pnpm check`, and can localize manifest text. WXT already
ships the i18n type scaffolding, so integration cost is low.

## Decision

We will adopt **`@wxt-dev/i18n`** (registered as the `@wxt-dev/i18n/module` WXT module) as the
localization layer. **`src/locales/<lang>.yml` is the single source of truth for all
user-facing text**, imported via the typed `#i18n` helper (`import { i18n } from '#i18n'`,
explicit per our `imports: false` convention). We ship a single locale, **French**, with
`manifest.default_locale: 'fr'`; **both the extension name and description are localized**,
via `__MSG_extName__` and `__MSG_extDescription__`, resolving at runtime from the compiled
`_locales/fr` catalog (`extName` = "Dreamland Reborn QoL"). The `beforeunload` prompt remains
browser-supplied and untranslatable (see `[[0008-beforeunload-exit-guard]]`).

## Consequences

- Adds a build-time dependency (`@wxt-dev/i18n`) and a compile step; the extension now emits
  `_locales/fr/messages.json` on both the Chrome MV3 and Firefox MV2 targets.
- Every new user-facing string must go through a locale key rather than a literal — adding a
  feature now includes adding its `features.<camelCaseName>.name`/`description` keys to
  `src/locales/fr.yml` (the "Adding a feature" checklist in `CLAUDE.md` is updated to match).
  Key segments must be camelCase, not the kebab `Feature.id` — compiled message-key names
  allow only `[A-Za-z0-9_]`.
- `i18n.t(...)` is type-checked against the generated keys, so a typo fails `pnpm check`. Keys
  are regenerated by `wxt prepare` (which runs on `postinstall`).
- Adding another language later is a single new `src/locales/<lang>.yml` file — the reason this
  layer was chosen over translating literals in place.
